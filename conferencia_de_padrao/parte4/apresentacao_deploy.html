Configuração do Backend

Como configuramos o Render

📦 Tipo de serviço: Web Service com Docker

Configuramos o Render para usar o Dockerfile do backend. Toda vez que recebe um novo deploy, ele baixa a imagem do Docker Hub e sobe o container.

🔐 Variáveis de ambiente

VariávelPara que serve
DATABASE_URLString de conexão com o Neon
SECRET_KEYAssina os tokens JWT de login
JWT_TTL_HOURSTempo de expiração da sessão
CLOUDINARY_URLUpload de fotos dos alunos

🔔 Deploy automático via webhook

O Render gera uma URL secreta de deploy. Quando o GitHub Actions termina de publicar a nova imagem Docker, ele faz uma chamada para essa URL e o Render atualiza o sistema automaticamente.

🚀 Comando de inicialização

O servidor sobe com o comando:

uvicorn app.main:app --host 0.0.0.0 --port $PORT

Na inicialização, o FastAPI cria automaticamente as tabelas novas do banco que ainda não existem.

Configuração do Frontend

Como configuramos a Vercel

🔗 Integração com o GitHub

Conectamos o repositório do GitHub diretamente à Vercel. Ela detecta automaticamente que é um projeto Next.js e configura o build sozinha. Não precisamos de nenhum script extra.

🌐 Variável de ambiente na Vercel

VariávelValor em produção
NEXT_PUBLIC_API_URLURL do backend no Render

Esta variável diz ao frontend onde a API está. Em desenvolvimento local, aponta para localhost:8000.

🔄 Como funciona o deploy automático

⚙️ Para o backend

Temos um workflow (backend-ci-cd.yml) que faz duas coisas:

1
Verifica a qualidade do código
Ruff, Mypy e Pytest (mínimo 80% de cobertura)
2
Publica e faz deploy
Build Docker → Docker Hub → Webhook Render

🌐 Para o frontend

Temos um workflow (frontend-ci.yml) que verifica o código: ESLint, TypeScript e Vitest. O deploy em si é feito pela Vercel automaticamente — sem precisar de workflow para isso.

🔐 Secrets no GitHub

Configuramos no painel do GitHub os dados sensíveis que os workflows precisam:

SecretUsado para
DOCKER_USERNAMEPublicar no Docker Hub
DOCKER_PASSWORDPublicar no Docker Hub
RENDER_DEPLOY_HOOKDisparar o deploy

🔒 Nenhuma senha ou chave está escrita no código — tudo fica nos Secrets do GitHub e nas variáveis do Render

CI/CD no WebAEE

Da alteração ao sistema no ar — passo a passo

🔬 CI — O que verificamos automaticamente

1
Backend: Ruff + Mypy + Pytest
Linting, checagem de tipos e testes com cobertura mínima de 80%
2
Frontend: ESLint + TypeScript + Vitest
Lint, checagem de tipos e testes unitários dos componentes

✅ Se algum teste falhar, o deploy não avança. O código ruim não chega aos usuários.

🚀 CD — O que acontece após os testes passarem

3
Build da imagem Docker do backend
GitHub Actions compila o Dockerfile e publica no Docker Hub
4
Webhook dispara o Render
O Render baixa a nova imagem e substitui o container em execução
5
Vercel detecta o push e faz o deploy do frontend
Integração nativa — sem nenhum webhook manual necessário

⏱️ Linha do tempo real de um deploy

[00:00] 👩‍💻 git push para a branch main
[00:05] 🤖 GitHub Actions inicia os dois workflows
[01:30] ✅ Testes aprovados — CI passou
[02:00] 🐳 Imagem Docker publicada no Docker Hub
[02:10] ☁️ Render recebe webhook — Rolling Deploy inicia
[02:50] 🎉 Sistema atualizado em produção — zero downtime

🔁 Esse ciclo inteiro acontece automaticamente — sem nenhuma ação manual após o git push
